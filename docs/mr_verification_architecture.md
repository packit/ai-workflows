# MR Verification Agent

## Problem statement

Every Ymir-authored merge request runs a CI pipeline, and that pipeline is the
only part of the loop that tells us something no earlier step could already
know: whether the package still builds and still passes its tests with the
change applied. When it goes red, somebody has to open the job, scroll the log,
and decide whether the MR broke it or the infrastructure did. That is slow,
repetitive, and it is where the MR sits idle.

The MR verification agent does that first pass. It waits for the pipeline to
finish, and **only if it failed** reads the failing jobs' logs, decides whether
the failure is attributable to the MR, and posts one comment explaining it.

### What this agent deliberately does *not* do

It does not review the change. No patch-provenance check, no changelog check,
no `Release:`-bump check, no spec-file hygiene, no scope check. Two reasons,
both of which make a reviewer here actively harmful rather than merely
redundant:

1. **Those artefacts come from near-deterministic steps.** Changelog entries
   and patch additions are generated by code, not by judgement. A reviewer that
   flags one can only ask for the same step to run again — which produces the
   same output and the same complaint. That is a loop, not a review.
2. **Spec-file correctness is package-local.** Whether a `Release:` bump, a
   patch numbering scheme or a changelog format is *correct* depends on rules
   the package maintainer sets. Checking it properly means checking it against
   those rules — which is exactly what the step that writes the change already
   does, with the rules in hand. Re-litigating it afterwards from the outside
   produces confident, wrong findings.

So the agent's question is narrow and answerable: **the pipeline failed; why,
and was it us?**

## Design constraints

1. **Only speak on failure.** A green pipeline gets a label and nothing else.
   A bot that comments on every MR trains people to skim its comments.
2. **The watcher must not be able to modify what it watches.** Read-only tool
   set — no `create`/`str_replace`/`remove`, no `git_patch_apply`, no push
   tool, no Jira status tool, and explicitly no `retry_pipeline_job`: an agent
   that can retry jobs would paper over the failures it exists to explain.
3. **A broken watcher must never block a good MR.** Every failure path degrades
   to `inconclusive` plus a Jira label. Submitting the job is best-effort and
   wrapped in a `try`: it runs *after* the MR is already open, so nothing it
   does can fail the producing agent's run.
4. **Waiting is not failing.** Polls are tracked separately from retries, and
   the wait is bounded by a deadline stamped on the task when it is created.

## Architecture

```
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐
  │   Backport   │  │    Rebase    │  │   Rebuild    │  │  MR Consolidation│
  │    Agent     │  │    Agent     │  │    Agent     │  │      Agent       │
  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘  └────────┬─────────┘
         │  MR opened      │                 │                   │
         └─────────────────┴────────┬────────┴───────────────────┘
                                    │
                   tasks.try_submit_verification_job()
                                    │  (checks MR_VERIFICATION_ENABLED
                                    │   and ymir.yaml `verification`)
                                    ▼
              ┌───────────────────────────────────────────┐
              │ mr_verification_queue_delayed  (ZSET)     │
              │  score = when to check the pipeline next  │
              └───────────────────┬───────────────────────┘
                                  │ promote_due_tasks()
                                  ▼
              ┌───────────────────────────────────────────┐
              │ mr_verification_queue  (+ _todo twin)     │
              └───────────────────┬───────────────────────┘
                                  │ BRPOP [todo, normal]
                                  ▼
                       ┌───────────────────────┐
                       │ mr-verification-agent │
                       └───────────┬───────────┘
                                   │ issue_lock("lock:mr-verify:<url>")
                                   ▼
                    ┌─────────────────────────────┐
                    │ MRVerificationWorkflow      │
                    │  1. check_pipeline          │
                    │     ├─ running ──────────────► back to the delayed ZSET
                    │     ├─ success ──────────────► label only
                    │     └─ failed                │
                    │  2. collect_failure_evidence │
                    │  3. run_analysis_agent       │
                    │  4. publish_verdict          │
                    │  5. record_result            │
                    └──────────┬──────────────────┘
                               │
             ┌─────────────────┼──────────────────┐
             ▼                 ▼                  ▼
      MR comment +     Jira comment       completed_mr_verification_list
      MR label         (MR-caused only)   + analysed-pipeline marker
```

## Queue design

One ordinary Redis **list** queue consumed with `BRPOP`, plus a priority twin
and a delayed ZSET.

There is no c9s/c10s split. The other agents split per container because they
run `rpmbuild` and need a matching build root; this one reads CI results and
job logs and never builds anything, so a single deployment serves every branch.

The wait for CI lives in the **delayed ZSET**, not in a sleeping worker: a
worker that slept through a six-hour pipeline would hold a pod, a Redis lock
and a semaphore slot for six hours and lose the task on the next rollout. The
same `delayed_queue` helper the reproducer agent uses promotes jobs back onto
the list when they come due.

| Key | Purpose |
|-----|---------|
| `mr_verification_queue` | Jobs ready to check their pipeline now |
| `mr_verification_queue_todo` | Priority twin for `ymir_todo`-triggered runs |
| `mr_verification_queue_delayed` | ZSET of jobs whose pipeline is still running; score is the next check time |
| `completed_mr_verification_list` | `MRVerificationOutputSchema` records for inspection |
| `mr_verification_analysed_pipeline:<MR URL>` | `<pipeline id>:<sha>` of the last handled pipeline, so the same result is never reported twice. Expires after `MR_VERIFICATION_ANALYSED_TTL` (90 days) — the namespace has no eviction policy |

The verification queues are in `RedisQueues.input_queues()` but are deliberately
**excluded from the Jira issue fetcher's dedup scan**. These jobs sit in the
queue for as long as CI runs, often hours; a job waiting on a pipeline must not
stop a maintainer from re-triggering the issue with `ymir_todo`.

## Workflow steps

1. **`check_pipeline`** — one call to `get_merge_request_pipeline_status`. This
   is the only step most jobs ever run.
   - *Still pending/running* → if the deadline has passed, record `timed_out`
     and stop; otherwise return `wait_again` and the task goes back on the
     delayed ZSET. Nothing is cloned, nothing is published.
   - *Already handled* (same pipeline id and SHA) → skip. A new push means a
     new pipeline, which is checked again.
   - *success / skipped / manual* → verdict `ci_passed`, label, no comment.
   - *canceled, or anything else terminal* → `inconclusive`, no comment.
   - *failed* → collect evidence from the jobs that actually block the
     pipeline (`allow_failure: false`).
2. **`collect_failure_evidence`** — only on the failure path, which is why the
   expensive parts live here: clone the MR's source branch, fetch the target
   branch (plus the usual 60 s NFS attribute-cache wait), compute
   `git diff <target>...HEAD`, and pull the tail of each failing job's log with
   `get_pipeline_job_log`.
3. **`run_analysis_agent`** — the LLM reads the job logs, attributes the
   failure, and returns a `CIFailureAnalysis`. The diff is given as *context
   for attribution only*; the prompt says so explicitly and forbids reporting
   anything about the change that did not break CI.
4. **`publish_verdict`** — label the MR; comment only when CI failed; add a
   Jira comment only when the failure is attributable to the MR (an
   infrastructure flake is noise on the issue).
5. **`record_result`** — store the handled-pipeline marker and push the
   structured result onto `completed_mr_verification_list`.

## Verdicts, categories and labels

| Verdict | Meaning | MR label | MR comment |
|---------|---------|----------|------------|
| `ci_passed` | Pipeline terminal and not failing. | `ymir_ci_passed` | none |
| `ci_failed_mr` | At least one failing job failed because of this change. | `ymir_ci_failed` | yes (+ Jira comment) |
| `ci_failed_infrastructure` | Every failure is environmental or flaky. | `ymir_ci_infra_failure` | yes |
| `inconclusive` | Pipeline canceled, or the analysis could not be completed. | none | none |
| `timed_out` | The pipeline never finished within the wait budget. | none | none |

`inconclusive` and `timed_out` are deliberately unlabelled: an absent verdict is
honest, and labelling it would let a reader mistake "we could not check" for
"we checked". An agent crash that survives all retries sets the Jira label
`ymir_mr_verification_errored` and never touches the MR.

Per-job failure categories: `build`, `test`, `static_check`, `infrastructure`,
`flake`, `unknown`. A job is also marked `retryable` when re-running it is a
reasonable next action; when every failing job is retryable the comment says so.

## Per-package configuration

In `gitlab.com/redhat/centos-stream/rules/<package>/ymir.yaml`:

```yaml
verification:
  # Watch the CI pipeline of Ymir-authored MRs for this package and comment
  # when it fails. Default: true.
  analyze_ci_failures: true
```

Unlike `consolidation` and `reproducer`, verification defaults to **enabled**:
it only ever posts a comment on an already-red pipeline, so it is safe to opt
out of rather than into. A missing or malformed `verification` section falls
back to the defaults and is logged; it never stops the check.

## Global configuration

| Variable | Default | Effect |
|----------|---------|--------|
| `MR_VERIFICATION_ENABLED` | `true` | Kill switch. When false, producing agents stop enqueueing; already-queued jobs still drain. |
| `MR_VERIFICATION_INITIAL_DELAY` | `300` | How long after the MR is opened the first pipeline check happens. |
| `MR_VERIFICATION_POLL_INTERVAL` | `300` | Delay between checks of a running pipeline. |
| `MR_VERIFICATION_MAX_WAIT` | `21600` (6 h) | Wait budget, stamped on the task at submission. |
| `MR_VERIFICATION_MAX_JOB_LOG_CHARS` | `20000` | Tail of each job log pasted into the prompt. |
| `MR_VERIFICATION_MAX_FAILED_JOBS` | `5` | How many failing jobs are analysed. |
| `MR_VERIFICATION_MAX_DIFF_CHARS` | `20000` | Diff budget — attribution context, not a review. |
| `MR_VERIFICATION_ANALYSED_TTL` | `7776000` (90 d) | Lifetime of the already-analysed marker. |
| `CHAT_MODEL_MR_VERIFICATION` | `""` | Per-agent model override. |

## Running the agent

Against a single MR, without touching GitLab or Jira:

```bash
make run-mr-verification-agent-standalone \
    MERGE_REQUEST_URL=https://gitlab.com/redhat/rhel/rpms/bash/-/merge_requests/42 \
    JIRA_ISSUE=RHEL-12345 \
    SOURCE_AGENT=Backport \
    DRY_RUN=true
```

In direct mode there is no Redis, so a running pipeline is waited for with an
in-process sleep (same interval and deadline) instead of the delayed queue.

In the full pipeline the agent runs under the `agents` compose profile as
`mr-verification-agent`; follow it with `make logs-mr-verification`.
On OpenShift: `deployment-mr-verification-agent.yml`,
`make -C openshift logs-mr-verification`,
`make -C openshift show-mr-verification-queue`.

## Safety invariants

| Invariant | How it is enforced |
|-----------|--------------------|
| The watcher never modifies the MR branch | Read-only tool set; no push/edit/patch-apply tools are passed to the agent |
| The watcher never hides a failure by retrying it | `retry_pipeline_job` is not in the allowed tool list |
| The watcher never reviews the change | Prompt forbids it; the diff is labelled attribution-only and capped |
| A failed check never fails the producing agent | `try_submit_verification_job` catches everything and logs |
| A failed check never blocks the MR | Crashes produce a Jira label only; no MR label, no MR comment |
| Waiting never consumes retry budget | `poll_count` in the task metadata is separate from `Task.attempts` |
| Waiting is bounded | `deadline_at` is stamped at submission; re-queued polls cannot extend it |
| The same MR is never handled twice concurrently | `issue_lock` on the MR URL |
| The same pipeline result is never reported twice | `<pipeline id>:<sha>` marker in Redis |
| A pending check never blocks re-triage of the issue | Verification queues are skipped by the fetcher's dedup scan |
| In-flight checks survive a rollout | `run_task_loop(shutdown_event=…)` re-pushes to Redis on SIGTERM; `terminationGracePeriodSeconds: 45` |

## Alternatives and trade-offs

Every non-obvious decision in this feature, what else was on the table, and what
choosing it costs.

### Scope: CI triage only, versus full MR review

*Chosen:* watch CI, speak only on failure.
*Alternatives:* (a) the original full packaging review — patches, changelog,
`Release:`, scope; (b) a hybrid that reviews the change only when CI is green.

Trade-off: we give up catching mistakes CI cannot see (a changelog that
references the wrong issue still builds fine). We accept that because those
mistakes come from deterministic generators — the fix is to fix the generator,
not to add a second opinion downstream — and because judging spec changes
correctly requires the per-package maintainer rules that the generating step
already holds. The hybrid was rejected for the same reason: it has the same
false-positive problem, just at a less noticeable moment.

### Waiting: delayed ZSET, versus sleeping, versus webhooks

*Chosen:* re-queue onto a Redis ZSET and come back later.
*Alternatives:* (a) `asyncio.sleep` in the worker until the pipeline finishes;
(b) a GitLab webhook that pushes `pipeline` events to Ymir.

Sleeping is simpler and gives a faster reaction, but holds a pod, a lock and a
concurrency slot for hours and loses the task on every rollout. A webhook is
strictly better — no polling at all, instant reaction — but needs a public
endpoint, webhook configuration on every dist-git project, and secret
management; that is a separate piece of infrastructure, and the THREAT_MODEL
entry that comes with it. Polling costs one GitLab API call per MR per five
minutes, which is nothing at current volume. If MR volume grows an order of
magnitude, switch to webhooks and keep the polling path as the fallback.

Cost of the chosen interval: a failure can go unreported for up to
`MR_VERIFICATION_POLL_INTERVAL` (5 min). That is far below the time a human
takes to notice, so it is not worth tuning down.

### One queue, versus a c9s/c10s pair

*Chosen:* a single `mr_verification_queue` and a single deployment.
*Alternative:* keep the per-container split the other agents use.

The split exists so `rpmbuild` runs in a matching build root. This agent does
not build, so the split would buy nothing and cost a second pod's worth of
quota in an already-tight namespace. Trade-off: if a future version wants to
reproduce a build locally (`rpmbuild -bp`, a scratch build) the split has to
come back, along with branch-based queue routing. That is a contained change —
`get_mr_verification_queue()` is the only routing point.

### Blaming: LLM log triage, versus heuristics, versus "just link the job"

*Chosen:* an LLM reads the job logs and attributes the failure.
*Alternatives:* (a) regex/heuristic classification of known failure signatures;
(b) post the failing job links with no analysis at all.

Heuristics are cheap and deterministic but only recognise failures somebody
already catalogued, which is the long tail inverted. Linking only is honest but
adds nothing a maintainer could not get from the MR widget. The LLM can be
wrong, so the comment says so, quotes the log lines it based the call on, and
never blocks anything — a reader can check the evidence in one glance.

Log Detective's `extract_log_snippets` is used when the gateway has it
registered; it is strictly better than the LLM at finding the decisive lines in
a huge build log, but it is optional infrastructure, so it is an allowed tool
rather than a required step.

### Comment on success, versus silence

*Chosen:* label `ymir_ci_passed`, no comment.
*Alternative:* always comment with the verdict, including "all green".

A comment on every MR is a notification on every MR. The label carries the same
information, is filterable, and does not ping anybody. Trade-off: a maintainer
who wants proof the check ran has to look at the labels rather than the
discussion.

### Merge-blocking discussions

*Chosen:* dropped. Always a plain comment.
*Alternative (in the earlier revision):* a per-package `block_on_findings` flag
that posted blockers as an unresolved discussion.

A red pipeline already blocks the merge wherever the project requires one, so
an unresolved discussion adds friction without adding information — and it put
an AI verdict in the critical path of a human's merge button. Trade-off: for a
project that does *not* require green pipelines, Ymir's comment is advisory
only. That is the right default for an agent that can be wrong.

### Splitting `ymir_ci_failed` from `ymir_ci_infra_failure`

*Chosen:* two labels.
*Alternative:* one `ymir_ci_failed` label plus the comment text.

Two labels because the next action differs — fix the change versus retry the
job — and a label is what you can filter an MR list by. Cost: one more label in
the namespace, and a mislabelled MR if the attribution is wrong.

### Retrying flaky jobs automatically

*Chosen:* not done; `retry_pipeline_job` is deliberately withheld.
*Alternative:* let the agent retry anything it classified as `infrastructure`
or `flake`.

Tempting, and it would close the loop on the most common failure. Rejected for
now because a wrong `flake` classification turns into an infinite retry of a
real failure, and because the agent would then be judging its own work. The
comment says "retrying is probably all this needs" and leaves the button to a
human. Revisit with a hard retry cap once the classification has a track record.

### Reporting only MR-caused failures to Jira

*Chosen:* Jira comment only for `ci_failed_mr`.
*Alternative:* comment for every failure.

Watchers of the issue can act on "the change broke the build"; they can do
nothing about a dead runner. Trade-off: a long infrastructure outage is
invisible from Jira, visible only on the MR.

### Keeping the clone on the failure path

*Chosen:* clone (and fetch the target branch, with its 60 s NFS wait) only when
CI failed.
*Alternatives:* (a) always clone, as the first revision did; (b) never clone and
work from the GitLab diff API alone.

Always-cloning made the common case — a green pipeline — pay the most expensive
step for nothing. Never-cloning would remove the NFS wait entirely, but the
agent loses `git log` on the target branch, which is how it tells "this test
was already failing before us" from "we broke it". The failure path is the rare
one, so it can afford the cost.

### Naming

*Chosen:* the agent, module, queues and doc keep the "MR verification" name
even though the scope is now CI-only.
*Alternative:* rename everything to `mr_ci_verification`.

Renaming reads better and would prevent exactly the scope drift this feature
already had once. It was not done because the branch is unmerged and the churn
would touch compose, OpenShift, Makefiles and docs for a cosmetic gain. If the
name keeps inviting "could it also check…", rename it.
